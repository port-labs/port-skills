# Troubleshooting and common mistakes

Failure modes for the custom-UI login flow. The code is in [../assets/spa-example.md](../assets/spa-example.md), and the reasoning behind the popup design is in [popup-login-explained.md](popup-login-explained.md).

## Symptoms

| Symptom                                                                                                           | Likely cause                                                                                                                                                                                                                                                              |
| ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auth0 shows `"Callback URL mismatch"`                                                                             | `redirect_uri` sent to `/authorize` doesn't byte-for-byte match a registered URI (check scheme, host, port, and trailing slash) — or it's a live-preview URL that was registered but isn't actually the published/public one being used at runtime                        |
| Token exchange returns an error                                                                                   | Wrong `code_verifier` (the opener's pending login was cleared, e.g. the page reloaded mid-login) or the code was already used/expired                                                                                                                                     |
| Port API calls fail with a CORS error                                                                             | Either the app's redirect URI was registered/updated in the last ~30s and the CORS allowlist hasn't propagated yet (wait and retry), or the calling origin doesn't match any registered redirect URI and needs the proxy fallback (`../assets/port-proxy-fallback.md`) — see `pkce-flow.md` (Calling the Port API) |
| App redirects to `/` after login but still shows the login page                                                   | `AuthCallback` bypassed `exchangeCodeForTokens` and wrote to `localStorage` directly, so `PortAuthProvider`'s live state was never updated                                                                                                                                |
| Auth0 never redirects back at all — the callback URL seems unreachable                                            | The `redirect_uri` points at a live-preview origin gated behind the hosting platform's own login wall. Use the published/public URL instead — see `registering-the-app.md`                                                                                                                  |
| Port API calls return a bare `Forbidden` with no other detail (only relevant if using the proxy fallback in `../assets/port-proxy-fallback.md`) | The proxy endpoint itself is gated behind the hosting platform's preview/staging access control, so the request never reaches your proxy code — not a Port API or CORS issue. Publish the app or otherwise make the proxy route public                                    |
| `"<domain> refused to connect"` when logging in from an editor's live preview                                     | `login()` didn't use the default popup flow — something redirected the app's own iframe to `/authorize` directly instead. Auth0 refuses to be framed regardless. See `popup-login-explained.md`                                                                     |
| Login completes in the popup but the original tab never updates, or the callback seems to do nothing              | The opener ignored the `port-auth-code` message: `event.origin`, `event.source` (must be the popup it opened) or `state` didn't match, or the opener page reloaded and lost its in-memory pending login. See `popup-login-explained.md`                             |
| Token exchange fails with a bare `Failed to fetch`, request never even reaches Auth0                              | `/oauth/token` was called directly from the browser and this origin isn't in the app's Allowed Web Origins (common on dynamic preview subdomains). Proxy the exchange through `/api/port-token` (step 3.5 of [../assets/spa-example.md](../assets/spa-example.md)) instead                                                        |
| Auth0 returns `Service not found: <url>` from `/authorize` or `/oauth/token`                                      | Wrong `audience` for the environment — `audience` must be the region's confirmed `{PORT_API_BASE}` (see `registering-the-app.md`), not a production or guessed value                                                                                                      |
| Port API returns `404: User with id "me" was not found`                                                           | There is no `/v1/users/me` — look the user up by email via `/v1/users/{email}`, or read claims straight from the `id_token`                                                                                                                                               |
| `upsert_external_interface_app`/`revoke_external_interface_app` fails parameter validation                        | `clientId` was passed as `appId` — use the app's `id` field instead (see `registering-the-app.md`)                                                                                                                                                                                          |

## Common mistakes

If the user's own prompt asks for any of these, push back and use the approach in the example instead:

- **Calling `{PORT_API_BASE}` directly from the browser (step 6 of [../assets/spa-example.md](../assets/spa-example.md)) is correct, not a shortcut to fix.** Port's API dynamically CORS-allows the origin of any registered external interface app redirect URI, per [pkce-flow.md](pkce-flow.md) (Calling the Port API). Only reach for the proxy fallback (`../assets/port-proxy-fallback.md`) if the calling origin genuinely doesn't match any registered redirect URI — and if a direct call fails with a CORS error right after registering/updating the app, wait ~30s for the allowlist to propagate before concluding a proxy is needed.
- **Don't do the `/oauth/token` exchange itself straight from the browser when the platform has a server route available.** That endpoint's CORS is governed by Auth0's Allowed Web Origins, not the app's registered redirect URIs — dynamic preview origins are usually not on that list, and the failure (`Failed to fetch`) looks identical to a misconfigured app. Proxy it through `/api/port-token` (step 3.5 of [../assets/spa-example.md](../assets/spa-example.md)) instead; this is a different CORS surface than the Port API one covered in [pkce-flow.md](pkce-flow.md) (Calling the Port API), so don't conflate the two.
- **Don't treat `clientId` as arbitrary hardcoded config.** It's the value `upsert_external_interface_app` returned when the app was created, and it only works paired with the exact registered `redirectUri`. A mismatched port during local dev (e.g. `:3000` vs `:5173`) is a common failure — check this first if login redirects fail. It's also not the same value as `appId` — see the next point.
- **Don't pass `clientId` to `upsert_external_interface_app` (when updating) or `revoke_external_interface_app`.** Those calls take `appId`, which is the `id` field returned by `upsert_external_interface_app`/`list_external_interface_apps`, not `clientId`. Passing the wrong one fails parameter validation.
- **Don't guess the Auth0 domain or API base beyond the two confirmed EU/US production rows in the region table in `registering-the-app.md`.** For staging, self-hosted, or any other environment, and for namespaced JWT claim keys (e.g. assuming `https://getport.io/email` is a real claim), these are unverified — ask the user for both (or confirm from their own Port session) before writing code that depends on them. `audience` is always `{PORT_API_BASE}` itself (Port's API validates the JWT `aud` claim against its own base URL) — so a wrong/production-shaped `{PORT_API_BASE}` on a non-production environment fails with `Service not found: <audience>`, not a separately-guessable audience value.
- **Don't call `/v1/users/me`.** Port has no notion of "the current user" as an id — it 404s with `User with id "me" was not found`. Look the user up by email (decoded from the `id_token`) via `/v1/users/{email}` instead, or just read claims off the token directly if the full Port record isn't needed.
- **Prefer a silent refresh over an immediate logout on token expiry**, using the `refresh_token` from the `offline_access` scope, as shown in `PortAuthContext` (step 3 of [../assets/spa-example.md](../assets/spa-example.md)). Guard the refresh with a single in-flight promise: the app's refresh tokens rotate with no overlap period, so two concurrent refreshes (React StrictMode's double-mounted effect, or two tabs opening at once) send the same token twice, Auth0 treats the second use as reuse and revokes the whole token family, and the user is logged out.
- **Don't put `code_verifier` in the OAuth `state` param (or any URL).** `state` is sent to Auth0 in the `/authorize` URL and comes back in the callback URL, so a verifier there is visible in history and logs and no longer protects against a stolen `code`. Generate `state` as a separate random nonce, keep the verifier in the opener window's memory, and have the popup only relay `code` + `state` back (see `popup-login-explained.md`). The `sessionStorage` entry used by the popup-blocked top-level fallback is the only place the verifier is stored, and it is deleted on read. Tokens still belong in `localStorage` (as above).
- **Don't accept a callback without checking `state`.** The opener must compare the returned `state` to the one it generated, and that it came from the popup it opened, before exchanging the `code`. Otherwise a crafted `/callback?code=…&state=…` link can log the user in as someone else.
- **Default `login()` to a popup for every app, not just ones detected to be embedded in an iframe.** A `window.top !== window.self` branch that only pops up when framed is an unnecessary special case (the `window.top === window` check in the popup-blocked fallback is a different thing: it only decides redirect vs. "Allow popups") — always opening a new window is simpler, works identically outside an iframe, and happens to sidestep the iframe-framing failure automatically. See `popup-login-explained.md`.
- **Don't skip the `audience` param on `/authorize`.** Without it, Auth0 may return an opaque access token instead of a JWT scoped to the Port API, and the `Authorization: Bearer` call to `{PORT_API_BASE}` will be rejected.
- **Don't have `AuthCallback` write tokens to `localStorage` on its own.** `navigate('/')` after a successful login is a client-side route change, not a page reload — `PortAuthProvider` doesn't remount and re-read `localStorage`. Route the exchange through the context's `exchangeCodeForTokens` (step 3 of [../assets/spa-example.md](../assets/spa-example.md)) so its React state updates too; otherwise the user is bounced right back to `LoginPage` even though they're technically logged in.
- **Don't redirect the app's own window/frame to `/authorize`.** Always open a new window instead (see `popup-login-explained.md`); the only exception is the popup-blocked fallback when the app is the top-level window (`window.top === window`) — never inside an iframe. Inside an iframed live preview (Lovable/v0/bolt.new) a direct redirect fails outright, since Auth0 refuses to be framed, and the popup default avoids that case entirely rather than needing to detect and special-case it.
- **Don't assume the app's default/preview URL is reachable enough to serve as the OAuth `redirect_uri`.** Hosted app-builder platforms often gate the live-preview origin behind their own login wall. Publish the app and use its public URL for the `redirect_uri` (see `registering-the-app.md`) — otherwise Auth0's redirect fails before reaching any of this code, with symptoms that look like a registration mistake instead of what it actually is. The same reachability requirement applies to the proxy endpoint (`../assets/port-proxy-fallback.md`), but only if that fallback is actually in use.
